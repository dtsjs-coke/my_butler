# ADR-0001: 대시보드 "AP Usage" 지표를 Butler 프로세스 CPU 점유율로 재정의

- **날짜**: 2026-09-11
- **상태**: Accepted
- **대상**: `my_butler` 웹 대시보드 홈 화면 시스템 상태 카드
- **관련 파일**: `utils/system_status.py`, `api/templates/index.html`
- **관련 커밋**: `689590a`, `a7e3ae3`

---

## 배경 / 문제

웹 대시보드 홈(`api/templates/index.html`)의 "AP Usage" 카드는 **S9 기기 전체의 CPU 사용률**을 보여주려는 의도로 만들어졌다. 그러나 사용자가 "AP 사용량이 정상적으로 표시되지 않는다"고 보고했고, 조사 결과 **이 카드는 한 번도 실제 CPU 사용률을 보여준 적이 없었다.**

증상의 이력은 다음과 같다.

1. **최초 구현** — `top -n 1 -b` 출력을 정규식으로 파싱.
   ```python
   m = re.search(r'(\d+)%user\s+(\d+)%nice\s+(\d+)%sys', raw.replace(' ', ''))
   ```
   `raw.replace(' ', '')`로 공백을 전부 제거한 문자열에 `\s+`(공백 1개 이상)를 요구하므로 **구조적으로 절대 매칭될 수 없는 정규식**이었다. 두 번째 대안 정규식은 `%user,`처럼 쉼표를 요구했으나 Android toybox `top` 출력에는 쉼표가 없어 역시 실패. 결국 최종 폴백인 **하드코딩 `return {"percentage": 5}`**가 반환되어 대시보드에 항상 5%가 고정 표시되었다.

2. **1차 수정 (`689590a`)** — 정규식 버그를 고치는 대신, 리눅스에서 표준적인 `/proc/stat` idle/total tick 델타 방식으로 교체했다. **이때 `/proc/stat`의 가용성을 실기기에서 검증하지 않고 "리눅스이므로 당연히 읽힌다"고 가정한 것이 오판이었다.** 배포 후 대시보드는 5% 고정에서 **0% 고정**으로 바뀌었을 뿐 여전히 잘못된 값이었다.

3. **2차 조사** — 이 ADR의 근거가 된 S9 SSH 실측(아래).

## 검토한 대안과 기각 근거 (전부 S9 실기기 SSH 실측, 2026-09-11)

기기: Galaxy S9 / `Linux localhost 4.9.118-23583079 aarch64 Android` / 8 cores / `SC_CLK_TCK=100` / Termux(비루트, uid `u0_a251`)

| # | 대안 | 실측 결과 | 판정 |
|---|---|---|---|
| 1 | `/proc/stat` 전체 CPU tick 델타 | `head: cannot open '/proc/stat' for reading: Permission denied` | **기각** |
| 2 | `/proc/loadavg` 폴백 | `cat: /proc/loadavg: Permission denied` | **기각** |
| 3 | `os.getloadavg()` | `AttributeError: module 'os' has no attribute 'getloadavg'` — Android bionic에 `getloadavg(3)`가 없어 CPython이 해당 기능 없이 빌드됨 | **기각** |
| 4 | `top -n 2 -b -d 1` 요약 라인 파싱 | `yes > /dev/null`로 2코어 부하를 건 상태에서도 요약 라인이 **항상** `800%cpu 0%user 0%nice 0%sys 800%idle 0%iow 0%irq 0%sirq 0%host` — toybox `top`도 내부적으로 `/proc/stat`에 의존하므로 동일한 권한 벽에 막힘 | **기각** |
| 5 | `top` 프로세스별 `[%CPU]` 컬럼 합산 | 부하를 건 `yes` 프로세스가 목록에 나타나지 않고, 값이 `3.7%`로 부자연스럽게 균일(= `1/27`)하여 신뢰 불가 | **기각** |
| 6 | `dumpsys cpuinfo` | `dumpsys: command not found` (Termux는 앱 UID라 platform 바이너리 접근 불가) | **기각** |
| 7 | `psutil` 도입 | `psutil.cpu_percent()`도 내부적으로 `/proc/stat`을 읽으므로 #1과 동일하게 실패. 의존성만 늘고 해결되지 않음 | **기각** |
| 8 | **`/proc/self/stat` (utime+stime) 델타** | **읽기 가능.** busy loop 1초 실행 시 `99.0%`로 정확히 산출됨. 다른 PID(`/proc/<butler_pid>/stat`)도 동일 UID이면 읽기 성공 | **채택** |

**핵심 결론: 이 기기에서 "시스템 전체 CPU 사용률"은 비루트 Termux 권한으로 취득할 방법이 없다.** 삼성 커널의 SELinux/proc 제한 때문이며, 코드로 우회 가능한 문제가 아니다.

## 결정

**"AP Usage" 지표의 정의 자체를 바꾼다.** 기기 전체 CPU 사용률이 아니라, **취득 가능하고 검증된 값인 "Butler 프로세스가 점유한 CPU"**를 표시한다.

- 데이터 소스: `/proc/self/stat`의 `utime + stime` 누적 tick (프로세스의 모든 스레드 합계)
- 계산식:
  ```
  percentage = (Δticks / SC_CLK_TCK) / (Δwall_seconds × cpu_count) × 100
  ```
- **100% = 8코어 전부 점유** 기준으로 정규화. 1코어를 꽉 채워 쓰면 12.5%로 표시된다.
- 소수 1자리까지 표시(`round(pct, 1)`), 0~100 범위로 클램프.
- 첫 수집 주기에는 비교 대상이 없으므로 직전 캐시값을 유지하고, 2번째 주기(10초 뒤)부터 실제 값을 산출한다.

## 근거

1. **정직한 값이 잘못된 값보다 낫다.** 기존 구현은 5%(하드코딩) 또는 0%(취득 실패) 고정으로, 사용자에게 거짓 정보를 보여주고 있었다. 셋 중 유일하게 실측으로 검증된 소스를 쓴다.
2. **모니터링 목적상 오히려 더 유용하다.** 이 대시보드는 "S9 기기 상태판"이 아니라 "24/7로 돌아가는 내 Butler 서버의 상태판"이다. 기기 전체 부하보다 "내 봇 프로세스가 CPU를 얼마나 먹고 있는가"가 이상 징후(무한 루프, 폭주하는 백그라운드 태스크) 탐지에 직결된다.
3. **외부 프로세스 spawn이 사라진다.** 기존 `top` 호출은 10초마다 서브프로세스를 띄웠다. `/proc/self/stat` 읽기는 파일 I/O 한 번으로 끝나 구형 기기의 부하와 지연이 모두 줄어든다.

## 결과 / 영향

- **지표의 성격이 바뀌었다**: "기기 전체 부하계" → "Butler 서버 프로세스 전용 부하계". 이 카드의 값이 낮다고 해서 기기가 한가하다는 뜻은 아니다.
- 오해를 막기 위해 프론트엔드에 명시했다 (`api/templates/index.html`):
  - 카드 라벨: `AP Usage (Butler 프로세스)`
  - 툴팁(`title`): "안드로이드 권한 제한으로 기기 전체 CPU는 읽을 수 없어, Butler 프로세스가 점유한 CPU를 표시합니다 (100% = 8코어 전부 점유)"
- **평상시 0%대로 표시되는 것은 정상이다.** 실측상 Butler는 대부분 idle이며(10초간 delta 3 ticks ≈ 0.03초), 기기 전체도 `800%idle` 상태였다. 배포 전 실기기 검증에서 값이 `0.0% → 0.0% → 1.4% → 2.6%`로 정상 변동함을 확인했다.
- 시스템 전체 CPU를 보여주는 기능은 **포기**했다. 대시보드에서 기기 전체 부하를 알 수 있는 수단은 현재 없다.

## 이 결정을 뒤집으려면 (중요 — 같은 조사 반복 금지)

**위 8개 대안은 전부 2026-09-11에 S9 실기기에서 직접 실행해 확인한 결과다. 다시 조사하지 말 것.**

"AP Usage가 기기 전체 CPU가 아니네, `/proc/stat`으로 바꾸면 되겠다"는 판단은 이미 한 번 내려졌고(커밋 `689590a`) 실패했다. 이 결정을 뒤집어 **기기 전체 CPU 사용률로 되돌리려면 아래 중 하나가 선행되어야 한다.**

1. **root 권한 확보** (기기 루팅) — `/proc/stat` 직접 읽기 가능해짐
2. **ADB shell 경유 우회** — `adb shell`은 shell UID라 `/proc/stat`과 `dumpsys cpuinfo` 접근이 가능하나, 기기 자신에서 24/7로 유지하기는 부적합
3. **Termux:API에 CPU 조회 커맨드가 추가되는 경우** — 현재 `termux-api` 패키지에는 CPU 관련 커맨드가 없다 (`termux-battery-status`는 있음)
4. **기기 교체** — 다른 제조사/안드로이드 버전에서는 `/proc/stat`이 열려 있을 수 있다. **기기를 바꿨다면 `head -1 /proc/stat`을 먼저 실행해보고**, 읽힌다면 이 ADR을 Superseded 처리한 뒤 새 ADR을 작성할 것.

위 조건 없이 되돌리는 시도는 반드시 실패한다. 뒤집을 경우 이 파일을 수정하지 말고, 상단 상태를 `Superseded by ADR-000X`로 표시한 뒤 새 ADR을 추가한다.

## 부수적으로 확정된 사실 (재조사 방지용 메모)

같은 실측에서 다른 지표들도 함께 검증했다.

- **배터리 / 온도**: 정상. `termux-battery-status`가 `{'percentage': 100, 'status': 'FULL', 'temperature': 37.9}`를 반환하며 실패 로그 없음. 단 이 "온도"는 **배터리 온도**이지 SoC/AP 온도가 아니다 — `/sys/class/thermal`도 막혀 있어 SoC 온도는 취득 불가다.
- **저장공간**: 수집 로직에 버그 없음. `df -h`(231G/13G used/Use% 6%)와 `shutil.disk_usage`(230.72GiB/13.18GiB/5.7%)가 일치. 정수 절삭으로 인해 `df`보다 한 단위씩 작게 보이던 표시만 보정했다.
- **RAM**: `/proc/meminfo`는 **읽기 가능**하다. `/proc/stat`·`/proc/loadavg`가 막힌 것과 달리 meminfo는 정상 동작하므로, "proc 전체가 막혀 있다"고 일반화하지 말 것.
