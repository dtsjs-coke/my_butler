# ADR-0003: 배터리 가드를 정지하고 SmartThings 네이티브 Routine(시간 기반 토글)으로 대체

- **날짜**: 2026-09-18
- **상태**: Accepted
- **대체하는 결정**: [ADR-0002](0002-battery-guard-polling.md) (Superseded)
- **대상**: `my_butler` S9 과충전 방지 자동화
- **관련 파일**: `core/smartthings/battery_guard.py`, `butler_pro.py`
- **관련 커밋**: (미커밋 — 사용자 확인 후 커밋/배포 예정)

---

## 배경 / 문제

ADR-0002에서 만든 배터리 가드는 "S9 배터리 90% 이상 → 플러그 OFF, 30% 이하 → ON"을 SmartThings Personal Access Token(PAT)으로 제어한다. 설계 자체는 실기기에서 검증되어 의도대로 동작했다. 그런데 운영에 들어간 뒤 **토큰이라는 단일 실패 지점**이 현실화됐다.

### 1) 실제 장애: 토큰 만료 → 재점화 실패 → 폰 완전 방전

ADR-0002가 "미해결 리스크"로 적어둔 시나리오가 그대로 일어났다.

```
배터리 90% 도달 -> 플러그 OFF (성공, 토큰이 아직 살아 있던 시점)
    ...시간 경과, PAT 만료...
배터리 30% 이하 -> 플러그 ON 명령 -> 401 인증 실패 -> 충전 재개 실패
    -> S9 계속 방전 -> 폰 꺼짐(= Butler 서버 자체가 정지)
```

- ADR-0002가 "가장 먼저 의심할 것은 토큰 만료"라고 적어둔 예측은 맞았지만, **Discord 경고는 폰이 죽는 것을 막지 못했다.** 경고를 보내는 주체(Butler)와 죽는 주체(S9)가 같은 기기이기 때문이다.
- 이때 폰을 살린 것은 코드가 아니라 **SmartThings 앱에 따로 설정해 둔 백업 자동화**("플러그가 OFF로 N시간 지속되면 켜기")였다. ADR-0002에서 "유일한 확실한 안전장치"라고 적은 그 항목이다.
- 즉 **실전에서 실제로 기기를 살린 것은 SmartThings 클라우드 쪽 규칙이었고, 커스텀 폴링 로직이 아니었다.**

### 2) 구조적 문제: 토큰 갱신이 사람 손에 달려 있다

- PAT를 주기적으로 재발급해 **로컬 `.env`와 S9의 `.env` 양쪽에 손으로 반영**하고 봇을 재시작해야 한다(`sync_s9.py`가 `.env`를 동기화에서 제외하므로 자동화되지 않는다).
- 갱신을 잊으면 기능이 조용히 멈추는 정도가 아니라 **"플러그를 끈 상태로 멈춰서 폰을 죽이는"** 비대칭적 실패로 이어진다. OFF는 성공하고 ON만 실패하는 순서가 최악인데, 이 기능은 구조상 항상 OFF를 먼저 보낸다.
- 근본 해결(OAuth SmartApp + refresh token)은 공개 HTTPS 엔드포인트(Cloudflare 터널 의존) + SmartApp 등록 + 수명주기 핸들러 구현이 필요하다. **폰 한 대의 충전 타이밍을 맞추려고 감당할 복잡도가 아니다.**

## 결정

### 1. 커스텀 폴링 기반 배터리 가드를 **정지**한다 (삭제하지 않는다)

`core/smartthings/battery_guard.py`에 모듈 상수 `GUARD_ENABLED = False`를 두고, `start_battery_guard()`가 이 값을 보고 루프를 시작하지 않는다. `butler_pro.py`의 호출은 그대로 두며(함수가 스스로 판단), 정지 상태임을 PM2 로그에 한 줄 남긴다.

### 2. 대체 수단은 **SmartThings 앱의 네이티브 Routine**이다

사용자가 SmartThings 앱에서 직접 설정 완료: **4시간마다 플러그를 껐다 켰다 반복**하는 시간 기반 duty-cycle. 배터리 %를 보지 않는다.

- 실행 주체가 **SmartThings 클라우드**이므로 Butler 프로세스/PM2/Termux/S9가 전부 죽어도 계속 동작한다. ADR-0002에서 "코드로 완전히 막을 수 없다"고 적었던 그 위험이 구조적으로 사라진다.
- 토큰·`.env`·봇 재시작이 관여하지 않는다. 갱신할 것이 없다.

### 3. 되살리는 경로를 코드에 명시해 둔다

`GUARD_ENABLED = True`로 되돌리고 봇을 재시작하면 예전 동작이 그대로 복구된다. **단, 되살리기 전에 SmartThings Routine을 먼저 꺼야 한다** — 둘 다 켜져 있으면 루틴이 켠 플러그를 가드가 끄고, 가드가 끈 플러그를 루틴이 켜는 충돌이 발생한다. 이 경고는 코드 주석에도 적어 두었다.

## 검토한 대안과 기각 근거

### 정지 방법

| # | 대안 | 검토 결과 | 판정 |
|---|---|---|---|
| 1 | `data/battery_guard.json`의 `enabled`를 `false`로 | 이 파일은 `.gitignore` + `sync_s9.py` 제외 대상이라 **로컬에서 고쳐도 S9에 전달되지 않는다.** 폰에 직접 접속해 손으로 고쳐야 하고, 그 사실이 코드 어디에도 드러나지 않아 나중에 "왜 안 도는지"를 추적할 수 없다 | **기각** |
| 2 | `DEFAULT_BATTERY_GUARD_CONFIG["enabled"]`를 `False`로 | **동작하지 않는다.** S9에는 이미 `enabled: true`가 적힌 JSON이 존재하고, `load_battery_guard_config()`의 병합 규칙은 빈 문자열만 무시할 뿐 `true`는 그대로 파일 값이 이긴다. 기본값만 바꾸면 "껐다고 생각했는데 계속 도는" 상태가 된다 | **기각** |
| 3 | `butler_pro.py`에서 `start_battery_guard(client)` 호출을 주석 처리 | 확실히 멈추지만, 되살릴 때 import·호출부를 다시 손대야 하고 왜 주석인지가 모듈 쪽에서는 보이지 않는다. 호출부와 기능 설명이 두 파일로 흩어진다 | **기각** |
| 4 | 파일/디렉터리 삭제 | 되돌릴 수 없다. 루틴 방식이 안 맞을 가능성이 실재한다(아래 트레이드오프) | **기각** |
| 5 | **모듈 상수 `GUARD_ENABLED = False` + `start_battery_guard()` 초기 반환** | 스위치·설명·되살리는 법이 기능 파일 한 곳에 모인다. `sync_s9`로 S9까지 그대로 전달되고 git 이력에도 남는다. 정지 상태가 PM2 로그에 보인다 | **채택** |

### 대체 수단

| # | 대안 | 검토 결과 | 판정 |
|---|---|---|---|
| 1 | OAuth SmartApp으로 재설계해 토큰 자동 갱신 | 정공법이지만 공개 엔드포인트 + SmartApp 등록 + 수명주기 핸들러가 필요하다. 얻는 것(배터리 % 기반 정밀 제어)에 비해 유지보수 부담이 과하다. **다만 "배터리 % 기반이 꼭 필요하다"가 입증되면 이 방향이 1순위다** | 보류 |
| 2 | 토큰 만료를 감지해 자동으로 플러그를 ON 고정 | 401을 받은 시점엔 이미 명령을 보낼 수단이 없다. 인증이 죽었는데 인증이 필요한 복구를 하겠다는 모순 | **기각** |
| 3 | **SmartThings 네이티브 Routine (4시간 시간 기반 토글)** | 토큰이 관여하지 않고, 실행 주체가 클라우드라 S9가 죽어도 동작한다. 사용자가 이미 설정 완료. 설정·운영 비용 0 | **채택** |

## 근거 (요약)

1. **실전 데이터가 방향을 정했다.** 장애 순간 폰을 살린 것은 SmartThings 쪽 규칙이었고 커스텀 코드가 아니었다. 실제로 동작한 안전망 쪽으로 기능을 옮기는 것이 합리적이다.
2. **이 기능의 실패는 대칭이 아니다.** "덜 정밀하게 충전 관리"는 배터리 수명이 조금 줄어드는 문제지만, "재점화 실패"는 서버 자체가 죽는 문제다. 정밀도보다 **가용성**을 택한다.
3. **토큰은 사람의 주기적 개입을 요구하는 의존성이다.** 개인 프로젝트에서 "잊으면 서버가 죽는 수동 작업"은 언젠가 반드시 잊힌다.
4. **코드를 지우지 않는다.** 시간 기반 토글이 충분한지는 아직 모른다(아래). 실측 후 되돌릴 수 있어야 한다.

## 트레이드오프 / 남은 리스크

### ⚠️ 배터리 % 기반 판단을 완전히 포기한다

| | ADR-0002 (폴링) | ADR-0003 (루틴) |
|---|---|---|
| 판단 근거 | 실제 배터리 % (90% / 30% 임계값) | 시계만 봄 (4시간 주기) |
| 히스테리시스·데드밴드 | 있음 (31~89%에서 아무 동작 없음) | 없음 |
| 상태 확인 후 명령 | query-before-command로 중복 명령 없음 | 실제 상태와 무관하게 토글 |
| 토큰 의존 | 있음 (단일 실패 지점) | 없음 |
| S9가 죽어도 동작 | 안 함 | **함** |

**ADR-0002의 원래 문제의식은 그대로 유효하다**: S9에는 충전 상한 제한 기능이 없고, Termux 비루트 환경에서 sysfs 충전 제어에 접근할 방법도 없다. 이 결정은 그 문제를 **해결한 것이 아니라 근사치로 바꾼 것**이다.

**구체적 리스크 — 4시간 주기가 실제 충전 속도와 맞지 않을 수 있다.**

ADR-0002에서 실측한 수치로 계산하면 S9의 충전 속도는 대략 **2~3분당 1%**(≈ 시간당 20~30%p)다. 4시간 ON이면 이론상 **80~100%p**가 오른다.

- **과충전 쪽**: 50%에서 ON 구간이 시작되면 4시간 뒤엔 이미 한참 전에 100%에 도달해 만충 유지 상태로 방치된다 — 정확히 ADR-0002가 막으려던 상황이다.
- **방전 쪽**: 반대로 OFF 4시간 동안 소비가 예상보다 크면(폰이 Discord 봇 + Flask + 트레이딩 루프를 돌리는 서버라는 점을 감안) 다음 ON까지 30% 아래로 깊게 떨어질 수 있다.
- 두 위상이 실제 소비 패턴과 어긋나 고정되면 **"충전 사이클만 늘고 목표 구간에는 거의 머물지 않는"** 최악의 조합도 가능하다. 잦은 얕은 사이클 자체가 배터리에 유리하지는 않다.
- 게다가 **이제 이 상황을 감지할 주체가 없다.** 폴링 가드가 하던 Discord 경고가 사라졌으므로, 사용자가 가끔 SmartThings 앱이나 Butler 대시보드(`/api/system_status`)에서 배터리 추이를 직접 봐야 한다.

**검증 필요 (사용자 조치)**: 며칠간 하루 1~2회 배터리 %를 확인해 **최고점이 95% 이상으로 오래 머물거나 최저점이 20% 아래로 내려가지 않는지** 볼 것. 어긋나면 먼저 **루틴 주기를 조정**(예: ON 2시간 / OFF 4시간처럼 비대칭 duty-cycle)하고, 그래도 안 맞으면 `GUARD_ENABLED = True`로 폴링 가드를 되살리는 순서로 대응한다.

### 그 외

- **SmartThings Routine 자체가 이제 단일 실패 지점이다.** 사용자가 루틴을 지우거나 허브/계정을 갈아엎으면 안전망이 조용히 사라지고, 코드 쪽에는 아무 흔적도 남지 않는다. (ADR-0002의 백업 자동화도 여전히 살려 둘 것.)
- **`core/smartthings/client.py`는 그대로 둔다.** 정책이 아니라 통신 래퍼일 뿐이고, `test_smartthings.py`와 향후 재활성화에서 쓰인다.
- **`.env`의 `SMARTTHINGS_TOKEN`은 지우지 않는다.** 만료된 채로 남아도 아무도 호출하지 않으므로 무해하고, 되살릴 때 재발급 절차만 밟으면 된다.
- **`data/battery_guard.json`은 건드리지 않는다.** 로컬/S9 모두 그대로 두며, 이 파일의 `enabled` 값은 이제 **아무 효력이 없다**(코드 스위치가 먼저 걸린다). 되살릴 때 이 파일의 임계값·주기 설정이 그대로 재사용된다.

## 이 결정을 뒤집으려면

1. SmartThings 앱에서 **4시간 주기 Routine을 먼저 끈다.** (동시 실행 시 충돌)
2. `core/smartthings/battery_guard.py`의 `GUARD_ENABLED`를 `True`로 바꾼다.
3. `SMARTTHINGS_TOKEN`을 재발급해 **로컬 `.env`와 S9 `.env` 양쪽에 수동 반영**한다(`sync_s9.py`가 `.env`를 제외한다).
4. `sync_s9.py` 실행 후 S9에서 `pm2 restart` → `pm2 logs`에 `🔋 배터리 가드 시작 (폴링 주기 N분)`이 뜨는지 확인한다.
5. **토큰 만료 문제는 되돌아온다.** 이 경로를 선택한다면 ADR-0002의 "미해결 리스크" 절과 위 대안 표 1번(OAuth SmartApp)을 함께 검토하고, 그 결과를 새 ADR로 남길 것. 이 ADR을 고치지 말 것.
