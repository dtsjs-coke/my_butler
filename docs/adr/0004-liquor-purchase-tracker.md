# ADR-0004: 주류 구매 이력을 flat JSON + 편집 가능한 `product_key`로 관리한다

- **날짜**: 2026-09-18
- **상태**: Accepted
- **대상**: `my_butler` 웹 대시보드 — 주류 구매 이력 페이지(`/liquor`)
- **관련 파일**: `core/liquor_manager.py`, `api/flask_app.py`, `api/templates/liquor.html`, `data/liquor_purchases.json`, `dev_pjt/sync_manager/sync_s9.py`
- **상세 설계**: [liquor_purchases_design.md](../liquor_purchases_design.md)
- **관련 커밋**: (미커밋 — 설계 단계)

---

## 배경 / 문제

사용자가 2022-11부터 구글 시트로 손으로 관리해 온 주류 구매 이력 122행(일자/구매장소/술이름/용량/상품·행사/가격/외화/당시환율/비고)을 `my_butler` Flask 대시보드로 옮기려 한다. 요구사항의 핵심은 단순 CRUD가 아니라 **"같은 술의 구매가격이 어떻게 변했는지"를 보는 것**인데, 여기에 구조적 어려움이 있다.

1. **술이름 표기가 흔들린다.** 같은 제품이 `카발란 술리스트 비노바리끄` / `카발란 솔리스트 비노바리끄`처럼 다르게 적혀 있다.
2. **동시에, 비슷하지만 절대 합치면 안 되는 것이 섞여 있다.** `발렌타인 17년`과 `발렌타인 30년 RESTAGE`는 문자열 유사도가 높지만 가격대가 10배 넘게 차이 나는 다른 상품이다. 즉 "유사하면 합친다"는 규칙은 이 데이터에서 반드시 오작동한다.
3. **용량이 섞여 있다**(700 / 750 / 1000 ml). 병당 가격만으로는 가격 추이를 올바로 읽을 수 없다.
4. **데이터에 git 백업이 없다.** `my_butler/.gitignore` 첫 줄이 `*.json`이라 이 파일은 커밋되지 않는다. 손으로 수년간 쌓은 데이터인데 복구 수단이 저장 로직밖에 없다.

## 결정

### 1. 저장은 `data/liquor_purchases.json` flat 파일 (SQLite 도입하지 않음)

`{"version": 1, "liquor_purchases": [...]}` 형태로, 기존 `settlements.json`의 래핑 방식을 따른다. 122행 / 연 30행 증가 / 1인 사용 규모에서 SQLite는 얻는 것 없이 스키마·마이그레이션·드라이버만 추가한다.

단, `settlements.json`의 저장 방식을 **그대로 베끼지는 않는다.** 임시 파일에 쓴 뒤 `os.replace()`로 교체하고(원자적 쓰기), `threading.Lock`으로 감싼다(Flask가 `threaded=True`). 백업이 없는 데이터에 "쓰다가 죽으면 깨지는" 저장 루틴을 쓸 수는 없다.

### 2. 그룹핑은 **레코드에 저장된 편집 가능한 `product_key` 필드**로 한다

- CSV 가져오기 시 보수적인 정규화 함수로 초기값을 **한 번 계산해 저장**한다. 조회할 때마다 다시 계산하지 않는다.
- 원문 `name_raw`는 **항상 그대로 보존**한다.
- 정규화는 공백/전각/대소문자/잡음 토큰(`면세`, `증정` 등)만 건드리고, **숙성연수·제품코드(`17년`, `105`, `CS`)는 절대 제거하지 않는다.**
- 화면의 "술 이름 정리" 패널에서 유사한 이름 쌍을 **제안**하고, 사용자가 누를 때만 `POST /api/liquor_purchases/merge_key`로 일괄 병합한다. **자동 병합은 하지 않는다.**

근거: 잘못 나뉜 그룹은 사용자가 병합 버튼 한 번으로 고칠 수 있지만, 잘못 합쳐진 그룹은 **어떤 행들이 합쳐졌는지 사용자가 기억해내야** 풀 수 있다. 두 실패의 비용이 비대칭이므로 under-merge 쪽으로 기운다.

### 3. 가격 추이 차트는 `병당 가격` / `100ml당 단가` 토글을 **필수**로 제공한다

`price_per_100ml`은 저장하지 않고 화면에서 계산한다(`price_krw`, `volume_ml`의 순수 함수이므로 저장하면 원본 수정 시 어긋난다). 같은 이유로 연/월 등 파생값도 저장하지 않는다.

### 4. 집계 API를 만들지 않는다 — 전체를 한 번에 내려주고 화면에서 계산한다

`GET /api/liquor_purchases`가 전량(약 30KB)을 반환하고, 필터·집계·차트는 전부 JS에서 한다. 엔드포인트 수와 프론트/백 계약이 줄고, 필터를 바꿀 때 서버 왕복이 없다.

### 5. 차트 라이브러리는 **Chart.js 4.4.1을 신규 도입**한다 (버전 고정)

브리핑에는 "`vwap_dashboard.html`이 이미 Chart.js를 쓴다"고 되어 있었으나 **사실이 아니다.** 실제로는 TradingView 위젯(`s3.tradingview.com/tv.js`)이며, 이는 증권 차트 임베드 전용이라 임의 JSON으로 라인/도넛 차트를 그릴 수 없다. 이 프로젝트에 범용 차트 라이브러리는 없었다.

Chart.js를 택한 이유: 이 페이지가 필요로 하는 라인/막대/도넛/복합축을 모두 커버하는 최소 선택지이고, 기존 Tailwind·lucide와 동일하게 CDN `<script>` 한 줄로 끝나 빌드 도구가 필요 없다(이 프로젝트에는 프론트 빌드 파이프라인이 없다). `@latest`가 아닌 **버전 고정**은 어느 날 CDN 업데이트로 차트가 조용히 깨지는 것을 막기 위함이다.

### 6. 레코드 ID는 `uuid4().hex[:12]` — 기존 시간 기반 방식을 쓰지 않는다

기존 `manage_settlements()`는 `str(int(time.time() * 1000))`을 쓴다. **CSV 122행을 루프로 저장하면 ID가 대량 충돌한다** — Windows의 `time.time()` 해상도는 약 15.6ms다. ID 충돌은 "1건 수정했는데 여러 건이 같이 바뀌는" 형태로 나타나 원인 추적이 어렵다. ID는 화면에 노출되지 않는 내부 식별자이므로 형식이 기존과 달라도 사용자 영향이 없다. **일관성보다 정확성을 택했다.**

### 7. `data/liquor_purchases.json`을 `sync_s9.py`의 `exclude_list`에 반드시 추가한다

이건 선택이 아니라 **데이터 손실 방지 조치**다. 상세는 아래 "결과" 참고.

## 검토한 대안과 기각 근거

### 그룹핑 방식

| # | 대안 | 검토 결과 | 판정 |
|---|---|---|---|
| 1 | 자동 정규화만으로 그룹핑(저장 안 함) | `발렌타인 17년`/`30년`을 구분하면서 오타는 흡수하는 규칙은 존재하지 않는다. 사용자가 결과를 교정할 수단도 없다 | **기각** |
| 2 | 조회 시점 퍼지 매칭(Levenshtein/difflib)으로 동적 그룹핑 | 숙성연수만 다른 제품이 유사도 0.9를 넘어 **자동으로 합쳐진다.** 결과가 데이터에 남지 않아 교정도 불가능하고, 정규화 로직을 고치면 과거 차트가 조용히 바뀐다 | **기각(가장 위험)** |
| 3 | 상품 마스터 테이블 분리(`products.json` + `product_id` 참조) | 정규화 모델로는 가장 옳다. 그러나 마스터 CRUD 화면·고아 참조 정리·무결성 검사가 전부 따라온다. 1인 122행에는 과설계 | **기각** |
| 4 | `name_raw`를 그대로 그룹 키로 사용 | 요구사항("표기가 달라도 그룹핑")을 아예 만족하지 못한다 | **기각** |
| 5 | **저장된 편집 가능 `product_key` + 제안형 수동 병합** | 결정론적이고, 틀리면 사용자가 즉시 고칠 수 있으며, 고친 내용이 데이터에 영구히 남는다. 122행 규모에서 정리 비용은 몇 분 | **채택** |

### 외화 통화 처리

시트에 `외화 = $262`, `당시환율 = 42.5`인 행이 있다. USD 환율은 1,300원대이므로 **이 `$`는 달러가 아니라 대만 달러**다(구매장소 "대만 가퉁완주"와 일치). 기호만으로 통화를 확정하면 틀린다.

| # | 대안 | 검토 결과 | 판정 |
|---|---|---|---|
| 1 | 기호 → 통화 코드 매핑 후 enum으로 검증 | 위 사례에서 `$`를 USD로 확정해 **틀린 데이터를 확신을 갖고 저장한다.** 검증이 오히려 해가 된다 | **기각** |
| 2 | 통화 필드를 아예 버리고 원화만 저장 | 되돌릴 수 없는 정보 손실. 일회성 이관이라 원본 시트를 다시 파싱하기 번거롭다 | **기각** |
| 3 | **`fx_currency`를 검증 없는 자유 문자열 표시 라벨로 두고, 환율 크기로 추정하되 불확실하면 기호 원문을 그대로 저장. 사용자가 편집** | 정보 손실이 없고 틀려도 즉시 고칠 수 있다. 모든 지출 차트의 기준값은 `price_krw`이므로 통화 라벨이 틀려도 분석 결과가 오염되지 않는다 | **채택** |

추가로 `|price_krw - fx_amount × fx_rate| / price_krw > 0.15`이면 경고를 띄우되 **가져오기를 막지는 않는다.** 외화는 참고 정보지 검증 기준이 아니다.

### CSV 가져오기 실패 처리

| # | 대안 | 검토 결과 | 판정 |
|---|---|---|---|
| 1 | 한 행이라도 깨지면 전체 거부 | 사용자가 시트 고치고 재업로드를 반복해야 한다. 122행 일회성 이관에 최악 | **기각** |
| 2 | 깨진 행을 조용히 건너뛰고 저장 | 몇 건이 왜 빠졌는지 사용자가 영영 모른다. 나중에 "시트엔 있는데 대시보드엔 없는" 유령 차이가 생긴다 | **기각** |
| 3 | **`dry_run` 미리보기 → 확인 → 실행 2단계. 정상 행만 저장하고 실패 행은 행번호·컬럼·사유로 보고** | 저장 전에 결과를 볼 수 있고, 빠진 행을 시트에서 바로 찾아갈 수 있다 | **채택** |

여기에 `(date, name_raw, price_krw)` 자연키 기반 중복 건너뛰기를 더해, 실수로 두 번 업로드해 244행이 되는 사고를 막는다.

> **[2026-09-18 갱신] 이 문단의 자연키 기반 중복 건너뛰기는 [ADR-0005](0005-liquor-purchase-no-dedup.md)로 대체됨(Superseded by ADR-0005).** 사용자가 같은 날 같은 술을 여러 병 사서 병마다 행을 따로 기록해 온 실사용 패턴과 충돌한다는 것이 확인됨.

## 결과

### 좋아지는 것

- 그룹핑이 결정론적이고, 틀렸을 때 사용자가 **데이터에 남는 방식으로** 고칠 수 있다.
- `name_raw`를 보존하므로 나중에 그룹핑 전략을 통째로 바꾸고 싶어져도 원본에서 재계산할 수 있다. 이 결정은 **되돌릴 수 있다.**
- 원자적 쓰기 + 락으로, 백업 없는 데이터를 저장 중 크래시·동시 요청으로부터 보호한다.
- 새 엔드포인트가 6개뿐이고 집계 로직이 서버에 없어, 차트를 추가해도 백엔드를 건드리지 않는다.

### 감수하는 것

- 사용자가 최초 1회 "술 이름 정리"를 손으로 해야 한다(수십 개 키, 몇 분). 자동화하지 않기로 한 것이 이 설계의 핵심이므로 의도된 비용이다.
- Chart.js CDN 의존이 하나 늘어난다. 오프라인에서는 차트가 안 뜬다 — 단, Tailwind·lucide가 이미 같은 조건이라 새로 생기는 제약은 아니다.
- 데이터가 수천 행이 되면 전량 전송 방식이 한계에 부딪힌다. 연 30행 속도로는 수십 년치 여유가 있고, 그때 가서 집계 API를 추가하면 되며 그 변경은 프론트만 건드린다.

### 반드시 같이 해야 하는 조치 (데이터 손실 방지)

`sync_s9.py`의 `cleanup_remote_orphans()`는 **"로컬에 없고 제외 목록에도 없는 원격 파일"을 S9에서 삭제**한다. `data/liquor_purchases.json`은 `.gitignore`의 `*.json`에 걸려 git으로도 전달되지 않으므로, 제외 목록에 넣지 않으면 다음이 벌어진다.

```
S9 대시보드에서 122행 업로드 -> S9에만 파일 존재
    ...이후 아무 이유로든 sync_s9.py 실행...
로컬에 없음 + 제외 목록에 없음 -> orphan 판정 -> 122행 전부 삭제 (백업 없음)
```

따라서 `exclude_list`에 `"data/liquor_purchases.json"`을 추가한다. `settlements.json`·`battery_guard.json`이 이미 같은 이유로 등재되어 있으므로, 이는 예외 처리가 아니라 **이 프로젝트에서 런타임 데이터 파일이 따르는 표준 절차**다.

그 결과로 따라오는 운영상 제약 하나: **이 데이터는 로컬↔S9 간에 전달되지 않는다.** 즉 실제 122행 이관은 코드 배포 후 **S9에서 돌고 있는 대시보드(터널 URL)에 접속해서** 해야 하며, 로컬 업로드는 기능 테스트용일 뿐이다.

### 나중에 이 결정을 뒤집게 된다면

- 그룹핑을 마스터 테이블로 바꾸고 싶으면: `product_key`가 이미 사람이 정리한 결과이므로, 그 고유값들을 그대로 마스터 레코드로 승격시키면 된다. 정리 작업이 헛되지 않는다.
- 저장소를 SQLite로 바꾸고 싶으면: `core/liquor_manager.py`의 `load_purchases()`/`save_purchases()` 두 함수만 교체하면 된다. 라우트와 화면은 그대로다. 이를 위해 라우트에 파일 I/O를 직접 넣지 않았다.
