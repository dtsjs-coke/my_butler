# ADR-0005: 주류 구매 이력 CSV 가져오기에서 자연키 기반 중복 건너뛰기를 제거한다

- **날짜**: 2026-09-18
- **상태**: Accepted
- **대상**: `my_butler` 웹 대시보드 — 주류 구매 이력 페이지(`/liquor`)
- **관련 파일**: `core/liquor_manager.py` (`import_csv()`), `api/templates/liquor.html`
- **상세 설계**: [liquor_purchases_design.md](../liquor_purchases_design.md) (변경 이력 절 참고)
- **supersedes**: [ADR-0004](0004-liquor-purchase-tracker.md)의 "CSV 가져오기 실패 처리" 절 중 `(date, name_raw, price_krw)` 자연키 기반 중복 건너뛰기 부분
- **관련 커밋**: (미커밋)

---

## 배경 / 문제

ADR-0004는 "실수로 같은 CSV를 두 번 업로드해 122행이 244행이 되는 사고"를 막기 위해 `(date, name_raw, price_krw)` 자연키가 같은 행을 중복으로 간주해 건너뛰는 로직을 채택했다.

기능 구현 후 사용자가 실제 사용 패턴을 알려왔다: **같은 날 같은 술을 여러 병 구매했을 때, 병마다 개봉일/비운 날짜가 다르므로 의도적으로 행을 따로따로 기록해왔다.** 이 경우 일자·술이름·가격이 완전히 동일한 행이 여러 개 정상적으로 존재한다. ADR-0004의 dedup 로직은 이런 행들을 "중복"으로 오판해 실제 구매 기록을 조용히 유실시킨다 — 사고를 막으려던 로직이 더 큰 사고(정당한 데이터의 유실)를 만든 셈이다.

## 결정

**자연키 기반 dedup 로직을 완전히 제거한다.** CSV 가져오기는 파싱에 성공한 행을 전부 저장하며, "중복"이라는 개념 자체를 다루지 않는다.

- `import_csv()`에서 `existing_keys` 비교, 파일 내부 자연키 중복 체크를 모두 삭제.
- API 응답의 `skipped_duplicates` 필드는 프론트 하위 호환을 위해 형태만 남기고 항상 `0`을 반환한다.
- 프론트(`liquor.html`)의 미리보기/완료 요약에서 "중복" 관련 문구를 제거해 더 이상 존재하지 않는 개념을 사용자에게 암시하지 않는다.

## 검토한 대안과 기각 근거

| # | 대안 | 검토 결과 | 판정 |
|---|---|---|---|
| 1 | dedup 유지 + "정말 중복입니까?" 확인 팝업 추가 | 122행 첫 이관 시점엔 문제없지만, 이후 정기적으로 겪을 매 업로드마다 사용자가 "이건 진짜 같은 병이 아니다"를 매번 판단/클릭해야 함 — 정상 사용 흐름에 계속 마찰을 만든다 | **기각** |
| 2 | 자연키에 순번(같은 키의 n번째 항목)을 포함시켜 "몇 번째 동일 항목까지는 정상"으로 허용 | 사용자가 실제로 같은 날 같은 술을 3병 넘게 사는 경우도 있어 임계값을 정할 근거가 없고, CSV 재실행 시 몇 번째 항목까지 이미 저장됐는지 순서가 보장되지 않아 오히려 더 위험 | **기각** |
| 3 | **dedup 완전 제거. 재업로드 안전장치는 사용자의 몫으로 남긴다** | 가장 단순하고, 정당한 데이터를 절대 유실하지 않는다. 실수로 같은 CSV를 두 번 올리는 사고는 사용자가 목록을 보고 직접 지우면 되며, 삭제 API가 이미 존재한다 | **채택** |

## 결과

### 좋아지는 것
- 같은 날 여러 병 구매를 있는 그대로 기록할 수 있다 — 이번 기능의 실제 사용 목적(개봉일/비운 날짜를 병 단위로 추적)에 부합한다.
- "중복 건너뜀" 개념이 사라져 CSV 가져오기 동작이 예측하기 쉬워진다(파싱되면 저장된다, 그 이상도 이하도 아니다).

### 감수하는 것
- 같은 CSV를 실수로 두 번 업로드하면 그대로 두 배로 쌓인다. 안전장치는 가져오기 전 미리보기 화면에서 "이미 몇 건 있는지" 육안 확인 + 사고 시 개별 삭제 API로 정리하는 것뿐이다. 122행 수준의 개인 데이터에서는 감수할 만한 비용으로 판단.

### 나중에 이 결정을 뒤집게 된다면
재업로드 안전장치가 다시 필요해지면(예: 대량 데이터로 육안 확인이 어려워지면), 자연키 exact-match가 아니라 **"CSV 파일 단위 체크섬으로 완전히 동일한 파일의 재업로드만 경고"** 하는 방향이 이번에 배운 함정(같은 날 같은 술 여러 병)을 피할 수 있는 대안이다.
