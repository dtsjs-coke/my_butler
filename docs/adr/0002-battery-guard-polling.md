# ADR-0002: 배터리 가드 — 로컬 배터리 폴링 + SmartThings를 유일한 상태 진실 공급원으로 채택

- **날짜**: 2026-09-11
- **상태**: Accepted
- **대상**: `my_butler` 배터리 가드 (S9 과충전 방지 자동화)
- **관련 파일**: `core/smartthings/client.py`, `core/smartthings/battery_guard.py`, `config/config_manager.py`, `butler_pro.py`, `utils/security.py`, `test_smartthings.py`, `data/battery_guard.json`
- **관련 커밋**: (미커밋 — 배포 후 커밋 예정)

---

## 배경 / 문제

Galaxy S9는 Butler 서버로 24시간 켜져 있고 충전기에 상시 연결되어 있다. 그런데 **S9에는 '충전 상한 제한' 기능이 없다.** (최근 갤럭시의 "배터리 보호" 기능은 이 기기에 없고, Termux 비루트 환경에서 충전 제어용 sysfs 노드에 접근할 방법도 없다.) 결과적으로 배터리는 항상 100% 만충 상태로 유지되며, 이는 리튬이온 배터리 수명을 빠르게 깎는 조건이다.

사용자는 SmartThings 허브와 스마트플러그를 이미 보유하고 있고, S9 충전기가 그 플러그에 꽂혀 있다. 따라서 **소프트웨어로 "배터리 90% 이상이면 플러그 OFF, 30% 이하면 ON"을 구현하면 충전 상한 제한을 흉내 낼 수 있다.**

문제는 이 자동화를 **어떤 구조로** 만들 것인가다. 구체적으로 세 가지 질문에 답해야 했다.

1. 무엇을 트리거로 삼을 것인가 — SmartThings 이벤트(웹훅)인가, 로컬 폴링인가?
2. "플러그가 지금 켜져 있는가"를 어떻게 알 것인가 — 로컬에 기억해두는가, 매번 물어보는가?
3. 얼마나 자주 확인할 것인가?

## 검토한 대안과 기각 근거

### 결정 1 — 트리거 방식

| # | 대안 | 검토 결과 | 판정 |
|---|---|---|---|
| 1 | SmartThings 웹훅/이벤트 구독 (SmartApp 등록) | **트리거 소스가 애초에 SmartThings가 아니다.** 감시 대상은 **S9의 배터리 %**이고 SmartThings는 이 값을 모른다. 웹훅을 붙여도 알려줄 이벤트가 존재하지 않는다. 게다가 SmartApp 등록 + 공개 HTTPS 엔드포인트(Cloudflare 터널 의존) + 수명주기 핸들러 구현이 필요해 복잡도가 급증한다 | **기각** |
| 2 | SmartThings 기기 상태를 주기적으로 폴링 | 플러그 상태를 아무리 자주 물어봐도 배터리 잔량은 알 수 없다. 판단 근거가 되지 못한다 | **기각** |
| 3 | Termux crontab에 별도 스크립트 등록 | Butler 프로세스 밖에서 돌면 Discord 알림·설정 공유·배터리 캐시 재사용이 모두 불가능해지고, 운영 지점이 PM2 외에 하나 더 늘어난다 | **기각** |
| 4 | **로컬 배터리 캐시 폴링 + 행동 구간에서만 SmartThings 호출** | `utils/system_status.py`의 워커가 **이미 10초마다** `termux-battery-status`를 호출해 메모리에 캐시하고 있다. 이 값을 읽는 비용은 0이며, 데드밴드(31~89%)에서는 네트워크 호출이 아예 발생하지 않는다 | **채택** |

### 결정 2 — 플러그 상태를 어떻게 추적할 것인가

| # | 대안 | 검토 결과 | 판정 |
|---|---|---|---|
| 1 | 로컬 플래그(`plug_is_on: true/false`)를 JSON에 저장하고 "이미 꺼져 있으면 스킵" | 세 가지 경우에 전부 실제와 어긋난다: (a) 봇/PM2 재시작 시 플래그와 실제 상태가 다를 수 있음, (b) 사용자가 SmartThings 앱에서 직접 플러그를 조작하면 플래그가 거짓말을 함, (c) 명령은 접수됐으나 Zigbee 전달이 실패하면 플래그만 바뀜. **"플래그 동기화 버그"라는 문제 카테고리를 스스로 만들어내는 설계다** | **기각** |
| 2 | 봇 시작 시 한 번 실제 상태를 읽어 플래그를 복원 | (a)만 해결되고 (b)(c)는 그대로 남는다. 복원 로직이라는 추가 코드 경로만 생긴다 | **기각** |
| 3 | **query-before-command (매번 실제 상태를 물어보고, 이미 원하는 상태면 명령 생략)** | 위 (a)(b)(c)가 **구조적으로 발생 불가능**해진다. 시작 시 상태 복원 로직도 필요 없다. 비용은 행동 구간에서 GET 1건/주기 | **채택** |

**비용이 문제되지 않음을 실측으로 확인** (2026-09-11, 응답 헤더 `X-RateLimit-*`):

| 엔드포인트 | `X-RateLimit-Limit` | 5분 주기 사용량 |
|---|---|---|
| `/devices/{id}/components/main/capabilities/switch/status` | **10** (약 1분 창) | 분당 0.2회 = **한도의 2%** |
| `/devices/{id}/health` | 40 | 전환 실패 시에만 호출 |

### 결정 3 — 폴링 주기

| 주기 | 오버슈트(최악) | 평가 | 판정 |
|---|---|---|---|
| 1분 | 약 0.5%p | 이득 없이 호출만 5배. 100% 만충으로 며칠 방치되면 하루 1,440회 | 기각 |
| **5분** | **약 2~3%p** (90% 컷 → 최대 92~93%) | 배터리 수명 관점에서 90 vs 92는 무의미한 차이 | **채택** |
| 15분 | 약 5~7%p | 95% 이상까지 올라갈 수 있어 기능 취지가 훼손됨 | 기각 |

근거가 된 수치: 구형 S9의 충전 속도는 대략 **2~3분당 1%**.

## 결정

### 1. 로컬 배터리 캐시 폴링 방식을 채택한다

- `utils/system_status.py`의 `get_system_status_data()`가 반환하는 **캐시된 배터리 값**을 읽는다. `termux-battery-status`를 새로 호출하지 **않는다** (이 기기에서 해당 명령은 4초 타임아웃을 잡아야 할 만큼 느리다 — ADR-0001 참조).
- 폴링 루프는 `discord.ext.tasks`의 `@tasks.loop`로 구현하고, `butler_pro.py`의 `on_ready()`에서 기존 `news_loop` / `start_subscription_tasks`와 동일한 방식으로 시작한다.
- 네트워크 I/O는 `aiohttp`(비동기)를 쓴다. `requests`는 이벤트 루프를 막으므로 금지 (GEMINI.md 규칙).

### 2. 플러그 상태의 진실 공급원은 SmartThings 하나뿐이다

한 주기의 판단 절차:

```
1. enabled=false → 종료
2. 임계값 검증 (하한 >= 상한이면 안전을 위해 동작 중단 + 경고)
3. device_id 비어 있으면 → SmartThings 호출 없이 종료 + 경고 1회
4. 배터리 % = 캐시에서 읽기 (네트워크 호출 0건)
   └ 신뢰 불가(수집 전 / 0% / 범위 밖)면 이번 주기 건너뜀
5. 31~89% (데드밴드) → 종료.      ★ SmartThings API 호출 0건 ★
6. desired = (>=90 ? "off" : "on")
7. GET 실제 상태 (1건)
   └ actual == desired → 종료      ★ 중복 명령 구조적으로 불가능 ★
8. POST 명령 (1건)
9. 5초 대기 후 GET 재확인 (1건)
   ├ 성공 → last_action 저장 + Discord 알림
   └ 실패 → health 조회 후 "명령은 갔는데 기기가 안 바뀜" 경고
```

`data/battery_guard.json`의 `last_action`은 **기록/표시 전용**이며 판단에 사용하지 않는다. 이 원칙을 깨는 순간 위에서 기각한 로컬 플래그 방식으로 되돌아가는 것이다.

9번의 **명령 후 재확인**을 넣은 이유: SmartThings가 반환하는 `"ACCEPTED"`는 "클라우드가 명령을 접수했다"는 뜻이지 "기기가 실제로 동작했다"는 뜻이 **아니다**. 재확인이 없으면 Zigbee 전달 실패를 영원히 알아채지 못한다. 이 검증은 상태 전환 시점(하루 2~4회)에만 발생하므로 비용이 무시할 수준이다.

### 3. 폴링 주기는 5분을 기본값으로 하되 설정 가능하게 한다

`data/battery_guard.json`의 `poll_minutes`를 매 주기 읽어 `change_interval()`로 반영한다(재시작 불필요). 1~60분으로 클램프해 `0`이나 `9999` 같은 값이 들어가도 안전하다.

### 4. 개인 기기 식별자는 소스코드가 아니라 `.env`에 둔다

`device_id` / `device_label`의 기본값을 `os.getenv("SMARTTHINGS_DEVICE_ID", "")` / `os.getenv("SMARTTHINGS_DEVICE_LABEL", "")`로 읽는다.

- deviceId는 비밀번호는 아니지만 **"우리 집의 어떤 기기"를 가리키는 개인 식별자**이므로, git에 커밋되는 소스코드에 UUID를 박아두지 않는다. 토큰(`SMARTTHINGS_TOKEN`)과 같은 취급이다.
- `data/battery_guard.json`은 `.gitignore`의 `*.json` 규칙으로 커밋되지 않고, `sync_s9.py`의 제외 목록에도 추가되어 로컬↔원격 자동 덮어쓰기가 없다. 따라서 실제 값은 `.env`와 각 기기의 로컬 JSON에만 존재한다.

**여기에 딸린 함정을 병합 로직으로 막았다.** `.env`에 값이 없는 상태로 봇이 **한 번이라도** 실행되면 `device_id: ""`인 JSON 파일이 생성되고, 기존의 단순 `dict.update()` 병합("파일 값이 기본값을 덮어씀")으로는 그 뒤에 `.env`를 제대로 채워도 **파일의 빈 문자열이 계속 이겨서 영원히 동작하지 않는다.** 그래서 `load_battery_guard_config()`는 **파일 값이 빈 문자열이면 '설정 안 됨'으로 간주하고 기본값(=`.env` 값)을 유지**한다. 원격 S9에 JSON 파일이 아직 없는 첫 배포 시점이 정확히 이 위험 구간이었다.

### 5. 토큰은 `.env`에만 두고 암호화하지 않는다

`utils/vwap_crypto.py` 수준의 별도 암호화는 **적용하지 않는다.** VWAP 쪽은 증권사 자격증명이라 추가 암호화가 정당하지만, SmartThings PAT는 기존 `DISCORD_TOKEN` / `GEMINI_API_KEY` / `SRT_PW`와 동급이며 이들 모두 `.env`(git 제외, sync 제외)에 평문으로 있다. 하나만 다르게 취급하면 일관성만 깨진다.

대신 `utils/security.py`의 `SENSITIVE_PATTERNS`에 `SMARTTHINGS_TOKEN`을 추가해, 로그나 Discord 메시지에 토큰이 섞여 나가는 경로를 차단했다.

### 6. 에러는 종류별로 구분해 처리하고, 루프는 절대 죽지 않는다

| 상황 | 처리 |
|---|---|
| 401 / 403 인증 실패 | Discord 경고 **1회** + `.env` 토큰 재발급 안내. **기능을 자동으로 끄지 않는다** — 토큰만 고치면 다음 주기에 저절로 복구 |
| 404 기기 없음 | device_id 확인 안내 1회 |
| 429 한도 초과 | 로그만, 이번 주기 스킵 |
| 5xx / 네트워크·타임아웃 | 경고 1회 + 다음 주기 자동 재시도 |
| 예상 못한 버그 | 로그만 남기고 루프 생존 |

**`discord.ext.tasks`는 루프 본문에서 예외가 밖으로 새면 그 루프를 조용히 멈춘다.** 이 방어가 없으면 인터넷이 한 번 끊긴 뒤로 기능이 죽어 있는데 아무도 모르는 상태가 된다. 그래서 루프 본문 전체를 `try/except Exception`으로 감쌌다.

**한 주기 안에서 재시도하지 않는다.** 5분 뒤 다음 주기가 자연스러운 재시도 시점이며, 별도 백오프 로직은 복잡도만 늘린다.

알림 중복 제거는 `utils/system_status.py`의 `_log_once` 아이디어를 그대로 가져와, 같은 문제가 5분마다 반복돼도 **상태가 바뀔 때만** 알리고 해소되면 "복구" 메시지를 한 번 보낸다.

### 7. Discord 알림은 "상태 변경 + 장애" 둘 다 보낸다 (옵션 C)

채널은 기존 `config/constants.py`의 `STATUS_CHANNEL_ID`를 재사용한다(새 상수를 만들지 않음). 알림 전송 자체가 실패해도 예외를 밖으로 내보내지 않는다 — 알림 때문에 본체가 멈추면 주객전도다.

**무음(옵션 A)을 기각한 이유**: 이 기능은 조용히 고장 나면(토큰 만료 등) 아무도 모르는 채로 폰이 계속 100% 충전되거나 반대로 방전되는 종류의 기능이다. 실패를 알려주는 경로가 반드시 필요하다.

## 근거 (요약)

1. **트리거 소스가 로컬이므로 폴링이 자연스러운 해법이다.** 웹훅은 "SmartThings에서 일어난 일"을 알려주는 도구인데, 우리가 감시하는 사건("배터리가 90%를 넘음")은 SmartThings 바깥에서 일어난다.
2. **상태를 두 곳에 저장하지 않으면 동기화 버그가 생길 수 없다.** 로컬 플래그를 없앤 대가는 GET 1건이고, 얻는 것은 재시작 내성 + 수동 조작 내성 + 명령 실패 감지다.
3. **데드밴드 설계로 평상시 비용이 0이다.** 배터리는 대부분의 시간을 31~89% 구간에서 보내며, 이 구간에서는 네트워크 호출이 아예 없다.
4. **정직한 실패가 조용한 실패보다 낫다.** ADR-0001에서 얻은 교훈("5% 하드코딩으로 거짓 정보를 오래 보여줬다")을 반영해, 이 기능은 고장 났을 때 반드시 사용자에게 알리도록 설계했다.

## 결과 / 영향

### 실기기 배포 검증 (2026-09-11, S9 PM2)

```
[BatteryGuard 23:47:41] 🔋 배터리 가드 시작 (폴링 주기 5분)
[BatteryGuard 23:47:41] 배터리 77% — 조치 불필요 구간(30% ~ 90%). API 호출 없음.
```

- 루프가 `on_ready()`에서 정상 기동하고 설정된 5분 주기를 읽어들이는 것 확인
- 배터리 값을 캐시에서 정상적으로 읽어오는 것 확인 (77%)
- **데드밴드에서 SmartThings API 호출이 0건이라는 설계 전제가 실측으로 확인됨**

| 검증 | 내용 | 결과 |
|---|---|---|
| SmartThings API 연결 | `GET /v1/devices` — 기기 71개, 그중 `switch` capability 62개, `category=SmartPlug` 3개 | ✅ |

| 실제 제어 (`test_smartthings.py --control`) | 켜기 → 상태 확인 → 원래 상태(off)로 복원. **딸깍 소리, SmartThings 앱 상태 변화, S9 충전 아이콘까지 사용자가 육안 확인** | ✅ |
| 판단 로직 시뮬레이션 | 가짜 SmartThings/Discord로 대체해 28개 시나리오(히스테리시스, 경계값 90/30/89/31, 배터리 캐시 미초기화, 인증 오류 1회 알림, 명령 무반응 감지, 빈 device_id 스킵, 빈 값 함정 방지 등) 검증 | ✅ 전부 통과 |

> **전력계는 0.0W로 표시되었다.** 배터리가 100% 만충이라 미세 전류만 흐르거나 SmartThings의 전력 보고가 지연된 것으로 추정된다. 충전 아이콘이 확실히 떴으므로, **판단 기준은 전력값이 아니라 스위치 상태**로 삼는 원래 설계를 유지한다. 전력값은 진단 참고용으로만 읽는다(`get_power_watt()`).

### ⚠️ 남아 있는 구조적 위험 — "플러그 OFF 중 봇이 죽으면 폰이 죽는다"

**이 설계에는 코드로 완전히 막을 수 없는 위험이 하나 있다.**

> 플러그를 끈 상태에서 Butler 프로세스(또는 PM2, 또는 Termux 전체)가 죽으면 → 플러그를 다시 켜 줄 주체가 사라짐 → S9가 0%까지 방전 → **서버 자체가 꺼짐.** 그리고 폰이 꺼져 있으니 스스로 복구할 방법이 없다.

자기 자신이 죽는 상황이므로 프로세스 내부 로직으로는 해결할 수 없다. 대책은 다음과 같다.

| 대책 | 커버 범위 | 상태 |
|---|---|---|
| **SmartThings 앱의 백업 자동화**: "이 플러그가 OFF 상태로 12시간 지속되면 → 켜기" | **SmartThings 클라우드가 실행하므로 S9가 완전히 죽어도 작동한다. 유일한 확실한 안전장치** | **사용자가 직접 설정 (코드 밖, 별도 진행)** |
| 하한을 여유 있게 (30%) | 정상 동작 중 방전 여유 확보 | 적용됨. **20% 이하로 내리지 말 것** |
| 정상 종료 시 플러그 ON 복원 | PM2 재시작/수동 종료는 커버. **강제 종료(kill -9)나 OOM은 커버 못 함** | 미구현 (효과가 부분적이라 보류) |

**이 기능을 다시 손대는 사람은 위 백업 자동화가 여전히 살아 있는지 먼저 확인할 것.** SmartThings 계정/허브를 갈아엎으면 이 안전망이 조용히 사라진다.

### 그 외 영향

- **평상시 SmartThings API 사용량은 사실상 0이다.** 배터리가 행동 구간에 머무는 동안에만 5분당 GET 1건이 발생한다(측정된 한도의 2%).
- **사용자가 SmartThings 앱에서 플러그를 수동으로 켜도, 배터리가 90% 이상이면 5분 내에 다시 꺼진다.** 이는 기능의 의도대로지만 수동 개입을 막으므로, 필요할 때는 `data/battery_guard.json`의 `enabled`를 `false`로 바꾼다. (나중에 `!배터리가드 on/off` 명령으로 편하게 만들 예정)
- **Discord 명령어(`!배터리가드` 등)는 이번 범위에서 의도적으로 제외했다.** 자동화 루프가 실기기에서 검증된 뒤 별도 단계로 진행한다 (GEMINI.md의 "한 번에 여러 기능을 건드리지 않기" 규칙).
- **`config_manager.py`의 기존 버그 하나를 발견했으나 고치지 않았다**: `load_keywords()` 등이 모듈 전역 기본값 리스트를 그대로 반환하고, `butler_pro.py`가 여기에 `append()`를 하므로 `DEFAULT_KEYWORDS`가 오염된다. 배터리 가드 쪽은 `.copy()` 반환으로 막았지만, 기존 함수들은 이번 작업 범위 밖이라 손대지 않았다. **별건으로 처리 필요.**

## 이 결정을 뒤집으려면 (중요 — 같은 조사 반복 금지)

### "웹훅으로 바꾸면 더 실시간 아닌가?"

**아니다.** 감시 대상인 배터리 잔량은 SmartThings가 모르는 값이다. 웹훅을 붙여도 배터리 변화를 알려줄 이벤트가 존재하지 않는다. 이 방향을 다시 검토하려면 **먼저 "SmartThings가 S9의 배터리 잔량을 알 수 있는 경로가 생겼는가"에 답해야 한다.** (예: S9를 SmartThings 계정에 등록해 `battery` capability를 노출시키는 방법이 생긴 경우 — 현재 Termux 환경에서는 불가)

### "로컬 플래그를 쓰면 API 호출을 아낄 수 있지 않나?"

아낄 수 있는 것은 **행동 구간에서 5분당 GET 1건**뿐이다(측정 한도의 2%). 그 대가로 재시작·수동조작·명령실패 세 가지 버그 경로가 되살아난다. 명백히 손해다.

메모리 캐시로 절충하는 안도 검토했으나, 그 순간 "재시작에 강함"이라는 최대 장점을 잃으므로 기각했다.

### "폴링 주기를 1분으로 줄이면?"

오버슈트가 2~3%p에서 0.5%p로 줄어든다. **배터리 수명 관점에서 90% 컷과 92% 컷은 의미 있는 차이가 아니다.** 호출량만 5배가 된다. 바꾸려면 `poll_minutes` 설정만 고치면 되지만(코드 변경 불필요), 그럴 만한 근거를 먼저 제시할 것.

### 토큰 만료 관련 (미해결 리스크)

SmartThings는 **최근 발급되는 Personal Access Token에 짧은 만료(24시간)를 적용하는 정책**을 도입한 것으로 알려져 있다. 그러나:

- API로 토큰 메타데이터를 조회할 방법을 찾지 못했다 — `GET /personal/tokens`는 **404**를 반환한다.
- `GET /v1/locations`는 **403**을 반환한다(이 PAT에 location 스코프 없음). 기기 조회/제어에는 지장 없다.
- 사용자가 개발자 포털에서 확인했을 때 만료일이 표시되지 않아, **만료 없는 영구 토큰으로 판단하고 진행했다.**

**만약 이 기능이 어느 날 갑자기 멈추고 Discord에 인증 실패 경고가 뜬다면, 가장 먼저 의심할 것은 토큰 만료다.** 토큰을 재발급해 `.env`에 넣고 봇을 재시작하면 복구된다(로컬·원격 `.env` 양쪽에 수동 반영 필요 — `sync_s9.py`가 `.env`를 동기화 제외한다).

만약 토큰이 실제로 24시간마다 만료되는 것으로 밝혀지면 **이 ADR을 수정하지 말고** 상단 상태를 `Superseded by ADR-000X`로 표시한 뒤, OAuth SmartApp 방식으로 재설계하는 새 ADR을 작성할 것.

## 부수적으로 확정된 사실 (재조사 방지용 메모)

2026-09-11 조사에서 함께 확인된 것들.

- **SmartThings 계정 기기 현황**: 전체 71개. `switch` capability 보유 62개(조명·에어컨·세탁기 등 가전 포함), 그중 `category=SmartPlug`는 **3개뿐**이다. 나머지 39개의 `Switch` 카테고리 기기는 `on`/`off`/`1`/`2`/`timer`/`dark`/`light` 같은 이름의 c2c 가상 스위치로, 이름만으로는 용도를 알 수 없다.
- **측정된 rate limit**: 스위치 상태 조회 `X-RateLimit-Limit: 10`(약 1분 창), `/health` 조회 `40`. `X-RateLimit-Reset`은 창 종료까지 남은 **밀리초**로 보인다.
- **`GET /v1/locations` → 403.** 이 PAT에는 location 스코프가 없어 방(room) 이름을 조회할 수 없다. 기기 목록의 `roomId`는 UUID로만 얻을 수 있다. 기기 조회/제어에는 영향 없다.
- **플러그의 `powerMeter`는 신뢰할 수 있는 판단 근거가 아니다.** 충전 중에도 0.0W로 보고된 사례가 있다(위 참조). 진단 참고용으로만 쓸 것.
- **`data/battery_guard.json`은 `sync_s9.py`의 제외 목록에 추가됨.** 다른 런타임 데이터 JSON(`news.json`, `keywords.json` 등)과 동일한 취급이다. 파일이 없으면 `load_battery_guard_config()`가 `.env` 값을 기반으로 자동 생성하므로, 동기화하지 않아도 원격에서 정상 동작한다.
- **로컬 Windows의 `my_butler/venv`는 깨져 있다** — `pyvenv.cfg`가 존재하지 않는 `C:\Python314\python.exe`를 가리킨다. 로컬에서 봇을 직접 실행하려면 venv를 다시 만들어야 한다. (이번 작업에서는 별도 임시 환경으로 우회했고, venv는 손대지 않았다)
